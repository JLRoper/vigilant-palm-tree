## 2. The subsystem interface — corrected

Fable's plan doesn't address this; I originally proposed a uniform `{ subscribe, apply, teardown }`. That's wrong — many subsystems need only one or two of those methods. Replace with two orthogonal interfaces that modules opt into:

```ts
interface Subscribes {
  subscribe(bus: EventBus): Unsubscribe;
}
interface Applies {
  apply(cmd: Command): Promise<CommandResult>;
}
```

| Subsystem | Subscribes | Applies |
|---|---|---|
| Toolbar | ✓ | |
| HUD | ✓ | |
| Entity mirror | ✓ | |
| API client | | ✓ |
| GameSession (load/new) | ✓ | ✓ |
| Command dispatcher | ✓ | ✓ |
| Visual entity mirror | ✓ | |
| Screens (adventure, city, combat) | ✓ | ✓ (forward user gestures to commands) |

`boot/game.ts` composes generically: for every `Subscribes`, call `subscribe` and stash the unsubscribe handle; on shutdown, call them all. For every `Applies`, route commands through it.

## 3. `EngineCtx` — what's deliberately NOT in it today

The plan says `EngineCtx = { rng, catalog }`. Today that's sufficient, but the seam is thin. Explicit non-goals so the contract doesn't churn mid-reorg:

- **No `now()` / `tick` clock.** All time effects are turn-counted or day-counted (`day % 7` upkeep, etc.). If a future command needs "elapsed time since last X," add `ctx.tick: number` (deterministic — engine reads it from `state.turn` or `state.day`, not from `Date.now`).
- **No actor identity.** Combat events need an `actorSeat`; the engine reads it from `cmd.actor`, not from `ctx`. Keeps commands self-describing and replay-safe.
- **No access to network/storage.** Commands that need remote data (catalog versions, sprite assets) load it into `catalog` at boot. If something truly dynamic needs runtime lookup, add `ctx.factories: Record<string, () => Promise<unknown>>` rather than smuggling it through `rng`.

## 4. Phase ordering corrections to Fable's migration plan

Fable's Phase 2 says "carve `gameState.ts` into engine domains one at a time." That order is under-specified — `endTurn.ts` calls into every other domain, so extracting it first creates a new monster or circular imports. The mandated order:

1. `economy/*` and `charter/*` first (leaves — depend on nothing but state shape)
2. `settlement/*` next (depends on economy for income math)
3. `hero/*` next (depends on settlement for recruit, on map for movement)
4. `turn/endTurn.ts` **last** (orchestrates everything above)
5. `combat/*` parallel to hero (largely self-contained)
6. `init/newGame.ts` last (calls into all the above)

Fable's Phase 6 (catalog tables) is also misplaced. "More castle sizes" is a near-term owner goal. Move the catalog baseline into Phase 2: stub `catalog/buildingCatalog.ts` reading from a hard-coded array, add the table in the Phase 4 DB migration, swap to table-backed catalog in Phase 5. Otherwise the feature is blocked on the whole reorg.
