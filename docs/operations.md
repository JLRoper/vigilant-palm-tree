# Operations Guide

<!-- docs:verified 2026-11-03 -->

This guide covers local development and deployment. See [`AGENTS.md`](../AGENTS.md) for the complete workspace/test safety rules.

## Local Development and Database Safety

- Use Node.js 22+ and `npm install`; `npm run dev` starts the Vite client and API.
- **A freshly cut worktree arrives with no `.env` and no `node_modules`** — both are gitignored, so `git worktree add` carries neither, and the first command a card runs dies on a missing launcher: `predev`/`pretest` report `'tsx' is not recognized`, `npm run build` reports `'tsc' is not recognized`, and only pure-`node` scripts (`npm run docs:check`) run at all. `npm run worktree:setup` (`scripts/worktree-setup.mjs`) is the repo-owned preparation path for a new tree; it is idempotent, additive, and safe to re-run from any checkout. It seeds `.env` from `.env.example`, writes `PGDATABASE=game_poc_<branch-slug>` for a non-primary branch and creates that database in the shared `game_db` container (**the primary branch deliberately gets no private database**), allocates the three ports through `scripts/allocate-ports.ts`, and makes `node_modules/.bin` resolve. It never weakens the port or database rules: it delegates port allocation to the allocator and leaves any `PGDATABASE` already in `.env` alone.
- **One extracted install per box, shared by every worktree — and a missing `node_modules/.bin` is a repairable state, not a reinstall.** The primary checkout's `node_modules` is the install worktrees share (linked, not copied). An interrupted `npm install` there leaves every package extracted and the launchers gone, which is why `npm run build` fails from every tree at once; `npm run worktree:setup` regenerates `.bin` from the installed packages themselves (offline, additive, byte-identical to npm's own launchers — pinned by `test/core/worktreeSetup.test.ts`). When there is no usable install to share, the setup runs `npm install` in the worktree instead. Never reinstall the shared tree while another worktree is live.
- **`git worktree remove` on a tree whose `node_modules` is a junction onto the primary's install deletes entries INSIDE that install.** `scripts/worktree-setup.mjs` shares the install by junctioning a worktree's `node_modules` at the primary's, and git does not unlink a junction — it recurses through it and removes entries in NTFS name order, so `.bin` and `.package-lock.json` (dot-prefixed, first) go before anything else. At the first package Windows will not release — a loaded `esbuild.exe`/`tsx` under a live agent — git aborts with `error: failed to delete '<tree>': Invalid argument` and exit 255, leaving every package intact and exactly those two entries gone; that is why every tree sharing the install fails on `tsc`/`tsx` at once while no install is running, and it is what periodically re-broke the primary checkout (measured: a reap that removed 98 worktrees moved the primary `node_modules` mtime while every package kept its own, and `.bin` + `.package-lock.json` were gone for three later cards). With nothing in use the same command empties the shared install outright. **Unlink the `node_modules` link before removing any worktree** — both the panel's release path and a hand-run `git worktree remove` hit this, `--force` or not — and prefer a share that is not a junction.
- `.kilo/setup-script.ps1` is a thin `kilo worktree create` hook that forwards to `scripts/worktree-setup.mjs`, so a Kilo-cut checkout and a `git worktree add` checkout are prepared by the same code and the database name has one rule.
- Ports are allocated per worktree by `scripts/allocate-ports.ts`; use `npm run dev:status` to discover the current local URLs. Set `LAN_HOST=1` before `npm run dev` to bind the API to `0.0.0.0` for LAN access.
- **A port in `.env` must be one the OS will actually bind.** The allocator preserves existing values — rotating a port out from under a live dev server is the failure its idempotency rule exists to prevent — with one exception: a value the OS answers `EACCES` for is re-allocated to a fresh kernel-assigned port, because nothing can ever bind it. On Windows, `EACCES` means the port sits inside an excluded range (`netsh int ipv4 show excludedportrange protocol=tcp`), and those ranges are re-drawn at every boot: a hand-pinned port that worked yesterday dies today with `listen EACCES: permission denied 0.0.0.0:<port>`. Measured 2026-11-03, the primary checkout's `.env` held `54232/54233/54234` inside the then-current range `54144-54243`, and its browser suites could not start at all. Kernel-assigned ports are safe by construction: the OS never hands out one from a range it excludes. `test/core/allocatePorts.test.ts` pins the rule (EACCES re-allocates; `EADDRINUSE` is a live holder and is kept).
- **The primary checkout's dev server must not watch the worktree fleet.** `vite.config.ts` sets `server.watch.ignored` to exclude `.worktrees/`, `.kilo/`, `.agentboard/`, `local/`, `dist/`, `analysis/`, `design/`, `reviews/` and `sessionTracking/`, and re-states vite's own `**/.git/**` and `**/node_modules/**` defaults, because declaring the key replaces them rather than extending them. The dev server watches the whole checkout root and holds a document request until its initial crawl settles, so the PRIMARY checkout — the only root on this box that contains ~130 sibling worktrees, each a full tree — took 135252ms to answer its first `GET /index.html`, and every browser suite there died on `page.goto: Timeout 30000ms exceeded` at the very commit that passed from a worktree (2370ms for the same request). `test/core/viteWatchIgnored.test.ts` pins the list, loads the config the way vite does, and fails if an entry would ever swallow `src/`, `packages/`, `server/`, `index.html` or `vite.config.ts` itself.
- Local PostgreSQL uses the shared `game_db` container on host port 5432. `npm run db:up` starts it. Do **not** run `npm run db:down` unless explicitly authorized; other worktrees share it.
- A **pod** is a per-run copy of that stack — its own postgres, api and web, its own ports — created with `npm run pod:up`, seen with `npm run pod:list`, removed with `npm run pod:down -- <name>` or `npm run pod:prune`. Pods stay up until removed, are labelled `heroes.pod=<name>` (so `list`/`down`/`prune` can never touch the shared stack or another run's pod), and are the place to aim a database-wiping suite while other worktrees are live (`PGDATABASE=heroes_pod_<name>`). Full rule set and the env handoff: [`AGENTS.md`](../AGENTS.md) → "Per-run docker pods".
- The API applies `server/schema.sql` and the ordered migration set (`001` through `032`) during startup. Keep migrations idempotent because startup re-runs them.
- `.env` may target a remote gameserver. DB-backed tests must load `.env.test` after `.env` to pin `PGHOST=127.0.0.1`. The smoke test deletes every game except its own fixtures, so never aim tests at the shared remote server. `npm run test:all` and the per-suite scripts run under `tools/run-test.mjs`, which loads `.env.test` and then the gitignored **`.env.test.local`** into the run it spawns (a variable already exported in your shell still wins) and prints `PGDATABASE=<name> (from <source>)`: put `PGDATABASE=game_play_<hex>` in `.env.test.local` for the PRIMARY checkout, whose fallback is otherwise `game_poc` — the database the running dev stack and the DEPLOYED stack serve. It prints a `WARNING` line when a run is aimed at `game_poc`.

## Test Commands

- `npm test` runs the smoke test.
- `npm run test:unit` runs serial Node `node:test` suites.
- `npm run test:all` runs the browser/e2e suites through `tools/run-test.mjs all`, followed by unit tests.
- `npm run docs:check` checks maintained Markdown links/source paths (always) and `docs:verified` freshness markers (full mode for all docs; `--changed <path>` / `--changed-from <git-spec>` scope freshness to the docs owning the changed files, per the `DOC_OWNERSHIP` globs in `tools/docs-check.mjs`) without connecting to the database.
- `npm run test:scope -- --changed-from <git-spec>` (`tools/test-scope.mjs`) reports whether a changeset needs the test suites. Documentation and agent-tooling paths (`*.md`, `docs/`, `.kilo/`, `.claude/`, `.github/agents|hooks|prompts|skills/`, `sessionTracking/`, `reviews/`, `analysis/`, `feature-plans/`, `local/`, `scripts/hooks/`, and a version-only `package.json` bump) print `TESTS SKIPPED`; anything else prints `TESTS REQUIRED`. The pre-commit gate and the PR workflow both use it to skip tests for docs/agent-only changes.

The browser suite includes smoke, multiplayer, city view, settlements, AI defender, AI charter, log panel, uncharted mode, and visual regression. Avoid `npm run test:all` when another coordinated session is exercising the shared database.

## AI Driver and Multiplayer

New games with AI enemies persist `lobby.aiDriver: "server"` and a boot token. `server/app/aiDriver.ts` scans eligible games, drives commands through the trusted in-process command handler, and uses per-game PostgreSQL advisory locks to prevent concurrent drives. Heartbeats let the watchdog identify stale ownership; a new process boot token and stale-driver adoption allow recovery after process loss. Pool connection timeouts and bounded turn/action budgets keep a stalled database or AI pass from holding the API indefinitely. Unflagged legacy games may still use the browser-driven AI path.

Multiplayer state changes are pushed through SSE (`GET /api/games/:name/events/stream`) using PostgreSQL notifications as wakeups. Event rows remain the source of truth; client replay/cursor handling is shared with the polling path, which remains a recovery backstop. SSE is ordinary HTTP streaming, not WebSockets.

## Deployment and Versioning

- Build Docker images with `npm run docker:build`, not bare `docker compose build`. The wrapper resolves the Git commit on the host and passes it into the image; a bare compose build can stamp the fallback `dev` value. Redeploy with `docker compose up -d --remove-orphans api web` so any legacy `game_gateway` container is removed before `game_web` (`nginx:1.27-alpine`, `docker/Dockerfile` `web-runtime` stage + `docker/nginx.conf`) binds host port `5173`. `game_web` serves `/usr/share/nginx/html` (`/app/dist` symlinked) directly from disk on ports `80` and `5173` with `Cache-Control: public, max-age=31536000, immutable` on `/assets/` and proxies `/api/` directly to `api:3001` via Docker's runtime DNS resolver (`127.0.0.11`).
- The root `package.json` version is the app version. Use `npm run version:bump -- patch|minor|major|X.Y.Z`; it updates the package version and `CHANGELOG.md`. Release tags use `v<semver>`.
- **`package-lock.json` is not a second app version.** Its top-level `version` and its root entry's `packages[""].version` are npm's own copy of `package.json`'s — npm writes both from it and rewrites them on every `npm install` / `npm ci` (an install whose lock `version` disagreed still exits 0). `scripts/bump-version.mjs` deliberately does not write the lock, so the lock's `version` lags the package (`0.32.0` while the app is `0.39.11`) and a bare `npm install` on an otherwise clean tree shows a two-line diff in it. Both are expected: read the app version from `package.json`, never from the lock, and leave the lock's copies to npm. Nothing in the repo, the tooling or the CI reads them.
- Run the pre-commit gate before committing; it now includes the `docs:check` documentation gate. This documentation task does not commit or run the full build/test gate.
