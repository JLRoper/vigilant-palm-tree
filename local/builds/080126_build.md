# Build Review — 2026-08-01

Branch: `battle/platoon-stats`. Scope: full-project review — architecture, current feature state, gaps, and gameplay recommendations.

## 1. What this project is

**Fallows of Elysiam** (package name `heroes-js`) is a turn-based, hex-grid strategy game in the *Heroes of Might & Magic* mold: move a hero across a procedurally generated map, claim resource tiles by founding/capturing settlements, manage a per-turn economy, build up settlement interiors ("city view"), and fight other heroes.

- **Client:** Vite + vanilla TypeScript, hand-rolled Canvas 2D rendering (no game engine/framework).
- **Server:** Express + `pg` (Postgres), authoritative persistence + drift-safety recompute.
- **Shared:** `shared/combat/*` — an engine-neutral battle resolver imported by both sides.
- **Tests:** Node `node:test` unit tests (state, economy, combat, map) + Playwright E2E smoke tests.

Single-player core loop is solid and playable end-to-end. LAN multiplayer (lobby, per-seat turn gating, polling sync) landed 2026-08-01. The single biggest structural gap is combat: a good tactical engine exists but isn't reachable from the real game (detail in §4).

## 2. Architecture

### 2.1 Process/data flow

```
Browser (Vite SPA)                              Express API (server/)
  src/main.ts -> GameEngine                        server/index.ts -> routes.ts
      |                                                |
      |-- io/api.ts, io/auth.ts, io/assetApi.ts --fetch--> |    pg.Pool -> Postgres
      |                                                |    (schema.sql + migrations 001-008)
      |   state/gameState.ts (pure reducers)          |
      |       applyEndOfTurnDetailed() -------reconcile-------> server re-runs same reducer
      v                                                v
  TurnController (client-authoritative)      shared/combat/resolveBattle.ts
      |  builds/spends Heroes, Settlements    (imported by BOTH client sandbox
      |  emits events via core/eventBus.ts     and server's /resolve-battle route)
      v
  render/* draws every frame from GameMap + Hero entities
```

### 2.2 Client module layering (`src/`)

```
core/      pure math + pub/sub (hex grid, RNG, event bus, building registry) — zero deps on anything else
  |
  +-- state/     authoritative reducers: gameState.ts (1460 lines, single source of truth), turnController.ts
  +-- entities/  animated runtime objects: Hero, Settlement/Castle
  +-- map/       terrain, resource placement, GameMap, A* pathfinding, castle placement
  +-- economy/   income / consumption / settlement-rate math
  +-- systems/   per-tick behavior: movement tween, enemy wander
  +-- ai/        aiBrain.ts (adventure-map AI targeting)
  |
  render/    camera, sprite pipeline, city-building drawers (5 art styles), fog, minimap, territory outlines
  views/     ~25 DOM/canvas UI panels (HUD, toolbar, hero/settlement menus, city view, battle arena, modals)
  managers/  GameEngine + 7 orchestrators wiring state <-> render <-> views
  io/        the only layer that knows HTTP shape (api.ts, auth.ts, assetApi.ts, multiplayerSync.ts)
```

`render/` never imports from `systems/` or `views/`; `core/` never imports outward. `state/gameState.ts` is consumed identically by the client (`turnController.ts`) and the server (`routes.ts`), which is what makes the "server re-applies the same reducer" drift-safety model work.

### 2.3 Database (Postgres, `server/schema.sql` + 8 migrations)

`games` (JSONB blobs for heroes/settlements/players/activeCharters), `tiles`, `game_events`, `settlement_snapshots`, `resource_transactions`, `game_assets`, `unit_types`, `auth_codes`/`user_sessions`, and (as of migration 008) a `lobby` JSONB column for multiplayer seat claims.

Full module-by-module dependency map (kept current, more detail than this doc): [`docs/module-documentation-and-relationships.md`](../../docs/module-documentation-and-relationships.md).

## 4. The one thing worth fixing first

There are genuinely **two separate, non-trivial combat implementations** in this codebase:

1. `shared/combat/resolveBattle.ts` — the one every real game actually calls (via `server/routes.ts`'s `/resolve-battle`). Deterministic, tunable, type-triangle + counterattacks, well-tested. But it treats the hex grid as decoration: `pickTarget()` always attacks lowest-HP-living, never checks adjacency or LOS.
2. `shared/combat/manualBattle.ts` + `src/views/manualBattleArena.ts` — the actual tactical game (movement, BFS pathing, melee/ranged range checks, retreat, surrender w/ leave-behind, an AI heuristic). Fully built, fully tested, and explicitly scoped in its own header comment as dev-sandbox-only ("Test Battle").

Meanwhile, the production path a real player hits (`GameActions.startBattleFlow` -> `battleModal.ts` -> resolver -> `turnHooks.onBattleResolved`) throws the result away with a `console.log` and shows nothing — casualties happen with zero on-screen feedback. `battleModal.ts`'s copy is also stale, describing pre-engine "delete the defender" behavior that no longer happens.

The fix is wiring, not new design: point `startBattleFlow` at the already-built `battleResultCard.ts`, and correct the modal copy. Full writeup: [`local/analysis/copilot-combat-analysis.md`](../analysis/copilot-combat-analysis.md).

## 5. Ways we may still want to add

Roughly ordered by leverage (small wiring fix -> larger systems):

1. **Show battle outcomes to the player.** See §4 — highest ratio of impact to effort in the whole codebase right now.
2. **Fix `obstacleSeed` non-determinism in prod.** `server/routes.ts` seeds it off `Date.now()`, defeating the resolver's own "same seed -> same fight" guarantee — breaks any future replay/audit feature.
3. **A real unit roster + army system.** Everything downstream (food, recruitment economy, hero unit caps, arcane-dust sink) is blocked on this; docs sketch a 5-unit placeholder table but call it explicitly non-authoritative.
4. **Win condition.** Right now there's no way for a game to actually end — no elimination check, no turn-limit/score victory, no end screen. Even a minimal "last player with a settlement wins" would close the loop.
5. **Morale & fatigue as real combat stats**, or pull the placeholder bars — a bar that never moves reads as broken, not "coming soon" (`docs/morale-fatigue-plan.md` already has an implementation path).
6. **Speed/initiative-based turn order in combat.** Both engines currently strictly alternate attacker/defender regardless of unit speed, so cavalry has no first-strike advantage over peasants — `UnitType.speed` is already stored, just unused for turn order.
7. **Smarter battle AI.** `runAiTurn` is a single greedy "attack lowest HP" heuristic — no focus fire, no exploiting its own type-advantage, no retreat/self-preservation.
8. **Promote the manual arena from sandbox to real feature**, once (or instead of) fixing #1 — the positional/tactical texture (chokepoints, flanking, ranged back-row) is the thing that would make combat feel like the genre it's imitating, and the primitives already exist.
9. **Hero capture-for-ransom** instead of hero deletion on defeat — designed in `docs/heroes.md`/`docs/army.md`, not implemented.
10. **Event-bus migration** (`docs/event-system.md`) — mostly an internal-quality item, but it's the thing that would make future features (morale, fog, win conditions) cheap to add without threading more manual rebuild calls through 6 managers.
11. **WebSocket-based multiplayer sync** instead of 2s HTTP polling, plus a path beyond LAN (`LAN_HOST` bind only today — no NAT traversal/relay for internet play).
12. **Fog of war.** Deliberately deferred, but revisiting it is the single biggest lever for adding map tension — right now every resource tile is visible from turn one, so there's no scouting/exploration tension at all.
13. **Spend sinks for Arcane Dust.** It's collected but has no consumer yet (no spells, no arcane-tagged units in a real roster) — currently the resource ticks up with nowhere to go.
14. **Sound and music.** Entirely absent; even minimal ambient/UI-click audio would materially change how the game feels to play.

## 6. Smaller things worth changing

- **`docs/README.md`'s status table is stale** — city-view is marked "📋 Planned" but is fully implemented (buildings, upgrades, persistence, 5 art styles). Worth a pass to resync doc status against actual code before it misleads the next session.
- **`test/cityView.test.ts` has been failing on `main` for a while** per multiple session-tracking entries (2026-08-01), confirmed pre-existing/unrelated to recent changes each time it's hit — worth actually fixing rather than re-confirming it's pre-existing on every branch.
- **Combat tests aren't wired into `npm run test:all`** — `resolveBattle`/`manualBattle` test coverage exists and is solid but must be run directly; easy to silently regress.
- Per `docs/TODO-front-end-efficiency.md`: city-view buildings redraw every frame (immediate-mode). Not a current bottleneck, but flagged as the first thing to profile if a 15x15 castle with 50+ buildings ever feels slow.
